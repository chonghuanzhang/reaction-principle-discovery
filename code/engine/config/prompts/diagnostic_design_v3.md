# V3 Family Diagnostic Design Proposal

Propose only structured representative reactive-state candidates for the
supplied canonical v3 family. `condition_states` remains in the response schema
for compatibility but must be empty. Use only the supplied canonical family,
evaluation, reviewed Principle, qualified evidence, ranking-analysis, and
representative-inventory contracts.

Freeze 3 has not occurred. Do not request, infer, quote, embed, or use sealed
answer names, synonyms, structures, conditions, or outcomes. Do not use prior
project experiments or retrospective answers.

The model may identify chemistry candidates only through typed candidate fields.
Mechanistic-coordinate coverage, diagnostic contrasts, structural fingerprints,
cluster keys, and availability declarations are not authoritative model output.
Deterministic code hydrates them from a factory-attested per-candidate inventory
record whose structure identity was produced by an injected trusted
canonicalizer. Canonical structural aliases share one fingerprint and cluster
and cannot count as additional diversity. Model declarations cannot partition
coverage, change selection, grant `verified_available`, or grant `cleared`.
Each inventory record's evidence IDs must resolve within the exact attested
evaluation evidence and remain attached to that representative. Handling claims
remain untrusted and cannot replace canonical prerequisites.

The model must not assign or change a family classification, priority, score,
rank, review decision, execution result, diagnostic success, or freeze state.
Only exact dimension-qualified `(evidence_id, dimension, principle_id)` links
from an attested scored evaluation may carry a reviewed Principle into planning.
In particular, catalyst requirements and condition windows may be derived only
from Principles linked on `condition_compatibility`; Principles linked on other
dimensions cannot supply condition values. Deterministic code validates the
trust chain, classifies the plan, performs constrained set-cover selection with
stable tie-breaking, selects one to three representatives, derives unique
condition IDs and values, and enforces all stage gates.

For testable families, identify the smallest candidate set that can support a
diagnostic design; do not propose condition values. Deterministic code derives a
paired control that differs in exactly one mechanistic factor while every other
condition field remains identical. A chemistry plan is not executable until an
independent factory-attested readiness record binds the exact canonical
candidate, inventory record, inventory artifact, handling artifact, and complete
prerequisite set. Its inventory artifact digest must exactly match the bound
inventory record. Readiness identity is derived from canonical readiness content;
the caller's verification ID is provenance only. The executable plan core binds
the readiness record ID, content digest, inventory artifact digest, and handling
artifact digest, so any readiness-content change produces a different plan
digest. A verification ID cannot index different readiness content anywhere in
the supplied readiness set, including across families. Every supplied readiness
record is factory-identity and content-address verified before this global
index, even when its family is Excluded or Unknown and receives no chemistry.
`needs_verification`, `unavailable`, or any uncleared prerequisite must remain
visible as a blocking operational action.

Boundary families are explicitly labeled negative controls whose expected
outcome is target-product absence. Target-product confirmation for a Boundary
family falsifies that classification and requires reclassification; it is never
diagnostic success and never authorizes optimization. Excluded families receive
no experiment. Unknown chemistry receives only an evidence-acquisition or
source-revisit action before any chemistry.

Diagnostic success requires calibrated target-product analytics. Fluoride
release may be measured only as supporting evidence and cannot define success
alone. The design must include mass balance, uniquely identified
competing-product measurements, and observations that would falsify the
proposed interpretation. Execution results must provide a nonblank readout for
exactly every planned competing-product measurement ID, with no missing or extra
IDs, and must bind the exact plan digest, representative, condition, target
analyte and method, run artifact, and result artifact.

Only deterministic factory code may construct a family plan. Before result
recording, code re-verifies the live plan's factory identity, stable execution
digest, full-content digest, and nested content. Copied, reconstructed, or
mutated plans cannot authorize results. Only deterministic code may convert a
matching typed execution result into a factory-attested immutable record. Do not
construct a success record or propose optimization; optimization is permitted
only after code verifies an attested Priority-family success record for that
exact executable plan core.
